# 侧边栏控制面板交互方案草案

## 1. 背景与目标

P7 已完成多配置执行区的核心能力收口，当前已具备：

- 多配置加载与卸载。
- 多个执行控件显示与真实执行绑定。
- 执行控件位置持久化。
- 收起/恢复入口、贴边吸附和离页保持。
- 单任务互斥、权限撤销与无障碍断开后的异常收尾。

真实使用复验后，当前展开态执行控件已经通过紧凑化优化缓解了拥挤与遮挡问题，但后续如果继续演进交互，现有“多个执行控件 + 恢复入口”的壳层形态，仍需要先明确长期方向，再决定是否进入新一轮实现。

本草案目标是：

- 为“侧边栏控制面板”定义一个独立于 `P8` 的交互讨论范围。
- 明确侧边栏只解决哪些交互问题，不提前混入高级动作能力。
- 评估侧边栏与现有悬浮交互、多配置执行区和单任务执行模型的兼容边界。
- 给出一个推荐方向，并决定是否需要先做最小原型验证。

## 2. 本轮范围

本轮只做：

- 产出侧边栏控制面板交互方案草案。
- 梳理真实目标场景、兼容边界和最小推荐方向。
- 判断是否需要先做最小原型。

本轮不做：

- 不修改 Flutter 页面、MethodChannel 或 Android Overlay 代码。
- 不直接实现侧边栏控制面板。
- 不进入 `P8` 长按、滑动、延迟和高级连招。
- 不引入多任务并行、暂停/继续控件、完整视觉重设计或新的全局配置项。

## 3. 现状问题归纳

当前多配置执行区已经可用，但如果继续扩展交互，仍存在以下结构性问题：

1. 当前交互入口由“多个执行控件 + 收起恢复入口”组成，心智模型偏功能导向，后续再叠加更多入口时容易分散。
2. 执行中状态、停止入口、配置识别和未来潜在的扩展操作，暂时分布在多个悬浮控件上，后续可能再次出现密度上升。
3. 现有执行区更偏“直接点击执行”的最小链路，若未来进入 `P8`，动作能力入口和交互壳层可能发生重复返工。
4. 当前方案已经尽量减小遮挡，但如果未来需要加入更多状态或入口，单纯继续在执行控件上加内容的收益会越来越低。

## 4. 核心设计问题

侧边栏控制面板方案需要先回答以下问题：

1. 侧边栏是替代当前展开态执行控件，还是与其并存。
2. 侧边栏只承载全局控制入口，还是同时承载 profile 列表、执行状态和开始/停止入口。
3. 收起态与展开态如何切换，是否继续复用现有恢复入口语义。
4. 侧边栏与普通、简洁、极简三种悬浮交互模式如何兼容，是否只作用于多配置执行模式。
5. 侧边栏是否保持当前单任务执行模型，不引入并行执行、暂停/继续或高级动作入口。
6. 如果未来进入 `P8`，侧边栏是否可以作为动作能力入口壳层，而不要求当前阶段先落地 `P8`。

## 5. 方案候选

### 5.1 方案 A：侧边栏只做全局控制壳

方案描述：

- 保留当前多个 profile 执行控件作为真实执行入口。
- 新增一个侧边栏控制面板，只承载全局收起/展开、当前运行状态摘要和进入更多操作的统一入口。
- 侧边栏展开后不直接替代各 profile 执行控件，执行控件仍以当前方式出现。

用户路径：

1. 用户点击侧边栏入口。
2. 侧边栏展示当前运行状态与全局操作。
3. 用户如需启动某个 profile，仍点击对应执行控件。

优点：

- 对现有执行链路影响最小。
- 保留 P7 已验证的多执行控件心智，不需要一次性重做所有交互。
- 适合作为过渡方案，风险较低。

风险：

- 交互层级会增加一层，但执行入口仍是多个独立控件，整体复杂度未必明显下降。
- 如果后续还要把 profile 列表迁入侧边栏，可能产生二次调整。

影响范围：

- 主要影响 Android Overlay 布局与状态展示。
- Flutter 侧可能只需补充少量 UI 状态同步，不必立即重构 profile 执行模型。

### 5.2 方案 B：侧边栏统一承载 profile 控制

方案描述：

- 侧边栏展开后直接承载已加载 profile 列表、当前运行状态和开始/停止入口。
- 当前多个独立执行控件不再作为展开态主入口，而是收敛为侧边栏内部的 profile 项。
- 收起态保留一个更轻量的悬浮入口，用于恢复侧边栏。

用户路径：

1. 用户点击收起态悬浮入口。
2. 侧边栏展开，展示已加载 profile 列表和当前运行状态。
3. 用户在侧边栏内选择某个 profile 执行或停止。

优点：

- 交互壳层更统一，后续承载更多状态和入口时扩展性更好。
- 有机会显著减少悬浮控件分散带来的视觉负担。
- 如果未来进入 `P8`，更容易把动作能力入口挂接到统一面板。

风险：

- 需要重新定义“点击即执行”的最短路径，可能影响当前已经验证的使用习惯。
- 需要重新评估 profile 列表展示密度、拖动、遮挡和恢复入口语义。
- Flutter、MethodChannel 和 Android Overlay 的改动面都可能扩大。

影响范围：

- 会同时影响 Flutter 多点页文案与说明、Android Overlay 结构、可能的状态同步协议和真机验收矩阵。

## 6. 推荐方向

当前推荐优先采用 **方案 A：侧边栏只做全局控制壳**，理由如下：

1. P7 刚完成稳定收口，当前更适合先验证“侧边栏是否真的能改善交互”，而不是立即重构已验证的多执行控件主链路。
2. 方案 A 可以把“交互壳层调整”和“真实执行入口重构”拆开，避免把稳定收尾和新交互重设计混到一起。
3. 如果方案 A 的最小原型已经能显著改善入口统一性和状态感知，就不必过早进入更重的结构调整。
4. 即使未来决定走方案 B，方案 A 的验证结果也能帮助判断哪些全局信息值得进入统一侧边栏。

## 7. 最小原型建议

建议在方案草案确认后，先评估是否做一个最小原型；若做，原型只验证以下问题：

1. 侧边栏作为全局控制壳后，收起/展开入口是否更容易理解。
2. 当前运行状态和停止入口是否比现在更容易被发现。
3. 在不替换现有执行控件的前提下，侧边栏是否能减少“入口分散”的感受。
4. 新入口是否会引入新的遮挡、误触或状态切换负担。

最小原型不验证：

- `P8` 动作能力编排。
- 多任务并行。
- 新的防误触配置体系。
- 完整视觉稿或动效细节。

## 8. 兼容边界

侧边栏控制面板草案需要明确遵守以下边界：

- 只作用于多配置执行区，不改动单点模式稳定链路。
- 保持单任务执行模型，同一时间只运行一个 profile 任务。
- 继续复用已验证的权限检查、横竖屏可见校正、无障碍断开提示和异常收尾策略。
- 不要求当前阶段改变 profile 数据模型和持久化结构。
- 普通、简洁、极简三种悬浮交互若需要兼容，应优先采取“新增执行区壳层”的方式，而不是回退现有编辑模式交互。

## 9. 暂不做

本草案明确暂不进入以下能力：

- `P8` 长按、滑动、延迟和高级连招。
- 多任务并行执行。
- 暂停/继续控件。
- 防误触完整配置体系。
- 导入导出、分组搜索、复杂视觉重设计。
- 为单点模式引入新的侧边栏交互。

## 10. 草案验收标准

本轮文档阶段的验收标准为：

- 已明确侧边栏控制面板的目标问题与适用场景。
- 已明确本轮只做交互草案，不进入 `P8` 与代码实现。
- 已至少给出两个可对比的交互方向。
- 已给出推荐方向及理由。
- 已明确是否建议先做最小原型，以及原型只验证什么。

## 11. 下一步建议

- 若团队认同本草案方向，下一步建议先补一轮低保真交互草图或最小原型说明。
- 原型若确认有价值，再单独拆新的实现小阶段，明确 Scope、Plan、Acceptance Criteria 和真机验收项。
- `P8` 继续保持延期，等侧边栏控制面板方向稳定后再决定是否进入动作能力规划与实现。
