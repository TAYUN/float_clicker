# Float Clicker Codex AI 协作工作流

本文档只记录 Float Clicker 项目中与 Codex AI 协作相关的规则、目录结构和使用方式。

## 1. 核心结构

Float Clicker 的 Codex 协作体系由以下几类入口组成：

- `AGENTS.md`：项目级长期规则，定义 Codex 进入项目后必须遵守的协作原则、项目边界和交付格式。
- `.codex/agents/`：角色型子智能体配置，用于把复杂任务拆成探索、规划、实现、验证、汇总几个职责。
- `.codex/skills/`：可复用工作流，把多角色协作流程固化成可反复使用的技能。
- `docs/AI协作/`：AI 协作说明、工作流文档和新对话交接提示词。
- `docs/需求文档/`：业务需求、阶段设计和后续能力边界。
- `docs/development/`：架构、代码规范、测试和发布等工程规则。
- `docs/验收清单/`：人工验收和回归检查清单。
- `docs/调试问题/`：已定位过的调试问题、复现步骤、解决方案和排查经验。
- `docs/开发计划/Codex协作记录/`：每轮 Codex 计划、执行、验证和风险收敛记录。

推荐理解方式：

```text
AGENTS.md                       = 全局规则和项目上下文
.codex/agents/                 = 角色分工
.codex/skills/                 = 固化流程
docs/AI协作/                   = AI 工作流和交接入口
docs/需求文档/                 = 需求和阶段边界
docs/development/              = 工程规范
docs/验收清单/                 = 验收和回归清单
docs/调试问题/                 = 调试问题沉淀
docs/开发计划/Codex协作记录/  = 过程记录
```

## 3. 关键文件说明

### `AGENTS.md`

Codex 进入项目时优先读取的总入口。

主要写：

- 当前项目状态。
- 必读文档。
- 核心协作规则。
- 当前阶段边界。
- 多角色协作说明。
- 项目代码规则。
- 验证命令。
- 交付输出要求。

适合放长期稳定规则，不适合放某一次任务的临时要求。

### `.codex/config.toml`

项目级 Codex 协作配置索引。

主要写：

- 全局规则文件位置。
- agents 目录位置。
- skills 目录位置。
- Codex 协作记录目录位置。
- 默认工作流。
- 当前开发焦点。
- 需要保护的稳定区域。
- 延后范围。

当前默认流程：

```text
explorer -> pm -> builder -> tester -> reporter
```

### `.codex/agents/*.toml`

角色型子智能体配置。

每个 agent 文件包含：

- `name`：角色名称。
- `description`：角色职责摘要。
- `developer_instructions`：该角色执行任务时的详细规则。

这些文件用于让复杂任务中的每个角色更专注，减少职责混杂。

### `docs/开发计划/Codex协作记录/`

Codex 每轮计划、执行和验收记录的落点。

适合记录：

- proposed plan 或计划模式输出。
- 多角色任务的范围、步骤、验收标准和假设。
- 自动化检查命令和结果。
- 真机验收步骤、通过项、失败项和未验证项。
- 发现问题后的复现步骤、影响范围、最小修复方案和剩余风险。

不适合记录：

- 长期规则，放进 `AGENTS.md`。
- 阶段总状态，放进 `docs/开发计划/多点模式开发阶段管理.md`。
- 一次性聊天内容或无结论的草稿。

### `.codex/skills/multi-role-feature/SKILL.md`

项目专属多角色功能开发流程。

必须包含：

```yaml
---
name: multi-role-feature
description: Float Clicker 复杂功能、多阶段任务、跨 Flutter/Android 改动的多角色协作流程。
---
```

主要写：

- 什么时候使用该技能。
- 标准执行流程。
- 当前阶段边界提醒。
- 发任务模板。
- 输出模板。

### `docs/AI协作/新对话交接提示词.md`

用于新开 Codex 对话时快速恢复上下文。

主要写：

- 当前项目状态。
- 已完成内容。
- 当前推荐下一步。
- 重要文档入口。
- 注意事项和阶段边界。

## 4. 角色分工

### Explorer

负责收集上下文。

重点：

- 读取 `AGENTS.md`。
- 阅读相关需求文档、阶段计划和验收清单。
- 查找 Flutter、Android、测试文件和 MethodChannel 协议。
- 总结当前实现、阶段边界和风险。

输出：

- 关键文件。
- 当前实现摘要。
- 当前阶段和文档约束。
- 依赖和风险点。

### PM

负责拆解需求和控制范围。

重点：

- 判断任务属于哪个阶段。
- 明确本次做什么、不做什么。
- 防止后期能力混入当前阶段。
- 定义验收标准。
- 需要形成计划时，在 `docs/开发计划/Codex协作记录/` 新建或更新本轮记录。
- 标出风险、假设和需要确认的问题。

输出：

- 任务拆分。
- 验收标准。
- 明确不做的内容。
- 风险和假设。

### Builder

负责最小化实现。

重点：

- 严格按任务范围修改代码。
- 遵循 `AGENTS.md` 和项目代码规范。
- 写必要中文注释，说明复杂逻辑、边界条件和设计取舍。
- Flutter 侧复用现有 feature 结构。
- Android 侧复用已稳定的悬浮窗、调度和异常收尾策略。

输出：

- 修改的文件。
- 主要实现点。
- 需要 Tester 重点验证的地方。

### Tester

负责验证和风险检查。

重点：

- 运行相关测试、lint 或静态检查。
- Flutter 改动优先运行 `flutter analyze` 和 `flutter test`。
- Android 原生改动考虑 `flutter build apk --debug`。
- 涉及悬浮窗、权限、无障碍、横竖屏时列出真机验收项。
- 涉及单点共享代码时补充单点回归项。
- 将验证命令、真机步骤、结果和剩余风险补充到本轮 Codex 协作记录。

输出：

- 已运行的验证命令。
- 结果摘要。
- 建议的真机验收项。
- 未验证项和剩余风险。

### Reporter

负责交付总结。

重点：

- 汇总改动。
- 汇总验证结果。
- 标注阶段状态。
- 标注风险、假设和未完成项。
- 标注是否涉及单点模式回归风险。
- 标注是否更新阶段管理文档和本轮 Codex 协作记录。

输出：

- 改动摘要。
- 验证结果。
- 阶段状态。
- 风险说明。
- 关键文件列表。

## 5. 标准执行流程

复杂任务按这个顺序执行：

```text
Explorer
  ↓
PM
  ↓
Builder
  ↓
Tester
  ↓
Reporter
```

对应动作：

```text
收集上下文
  ↓
拆任务 + 定验收标准 + 写入本轮计划记录
  ↓
实施改动
  ↓
验证结果 + 补充协作记录
  ↓
交付总结 + 确认记录路径
```

小任务可以合并角色，但仍保留这个基本顺序：

```text
先看上下文 -> 再定范围 -> 再改动 -> 最后验证和总结
```

## 6. 什么时候使用多角色流程

建议使用 `.codex/skills/multi-role-feature/SKILL.md` 的场景：

- 多点模式阶段开发。
- 跨 Flutter 和 Android 原生的任务。
- 涉及 MethodChannel、悬浮窗、无障碍点击、任务调度的任务。
- 需要保护单点模式回归的任务。
- 需要同步更新阶段计划、需求文档或验收标准的任务。
- 改动范围不止一个文件，且存在明显验证风险的任务。

可以不完整使用多角色流程的场景：

- 单个文档的小修正。
- 明确的小范围样式或文案调整。
- 不涉及行为变化的轻量整理。

即使不完整使用，也要先检查：

```powershell
git status --short
```

## 7. 计划和执行记录工作流

当任务进入计划模式、多角色流程或 P 阶段验收时，必须维护 `docs/开发计划/Codex协作记录/` 下的本轮记录。

命名建议：

```text
P阶段 任务名.md
```

示例：

```text
docs/开发计划/Codex协作记录/P5 剩余专项验收执行记录.md
docs/开发计划/Codex协作记录/P5 无障碍连接态同步收敛.md
```

计划阶段先写：

```text
Summary
Scope
Plan
Acceptance Criteria
Assumptions
```

执行后补写：

```text
Implementation Changes
Verification
Issues
Risks
Next Steps
```

职责边界：

- PM：创建或更新本轮记录，写计划、范围、验收标准和假设。
- Builder：如有代码改动，补充实现摘要和关键文件。
- Tester：补充验证命令、真机步骤、通过/失败项和未验证风险。
- Reporter：确认阶段管理文档和协作记录是否同步，并在交付中标注路径。

阶段总状态仍写入 `docs/开发计划/多点模式开发阶段管理.md`。协作记录只写本轮过程，避免阶段总表变成流水账。

### `docs/调试问题/`

已定位或反复出现的调试问题沉淀目录。

适合记录：

- 问题现象和触发条件。
- 复现步骤、设备信息、系统版本和权限状态。
- 已尝试但无效的排查路径，避免后续重复踩坑。
- 根因分析、最终修复方案和验证结果。
- 与悬浮窗、无障碍、横竖屏、设备连接、Flutter/Android 调试链路相关的专项经验。

不适合记录：

- 单轮任务计划和验收流水，放进 `docs/开发计划/Codex协作记录/`。
- 长期协作规则，放进 `AGENTS.md` 或 `.codex/skills/`。
- 尚无结论的零散猜测；可以先写进本轮协作记录，确认后再沉淀为调试问题文档。

### `docs/需求文档/`

业务需求、设计边界和后续能力规划的落点。

适合记录：

- 单点、多点、悬浮交互、外观配置等业务能力设计。
- 当前阶段做什么、不做什么。
- 后续能力的独立设计，例如多配置 profile。
- 影响 Flutter、Android 原生和 MethodChannel 协议的设计约束。

如果开发中发现需求或设计需要调整，需要同步更新相关需求文档、阶段计划和验收标准。

### `docs/验收清单/`

人工验收和回归清单目录。

适合记录：

- 真机验收步骤。
- 权限、悬浮窗、无障碍、横竖屏等人工检查项。
- 单点模式等稳定能力的回归清单。

每轮执行结果仍写进 `docs/开发计划/Codex协作记录/`；验收清单本身只维护可复用的检查标准。

### `docs/development/`

工程规范和开发约定目录。

适合记录：

- 架构边界、模块职责和目录分层。
- 代码风格、命名、注释和错误处理约定。
- 自动化测试、真机验收、发布流程。

这些文档是实现和评审时的工程依据，不承载某一轮任务的过程记录。

```text
请使用 Float Clicker 多角色流程完成这个任务。

目标：
[写清楚要做什么]

[相关阶段 / 文档 / 文件 / 报错]

阶段边界：
- 当前阶段：[P?]

- 本次不包含：[...]

约束：
- 先检查 git status。
- 先探索再实施。
- 不新增无关依赖。
- 不影响单点模式稳定行为。
- 改后必须验证。
- 如完成阶段任务，更新 docs/开发计划/多点模式开发阶段管理.md。

- 功能可用或文档更新完整。
- 测试或检查通过，无法验证的说明原因。
- 列出修改文件与风险。
- 列出本轮 Codex 协作记录路径。
```

## 10. 最实用的落地建议

- 长期规则写进 `AGENTS.md`。
- 固定流程写进 `.codex/skills/`。
- 角色职责写进 `.codex/agents/`。
- 新对话上下文写进 `docs/AI协作/新对话交接提示词.md`。
- 每轮计划、执行和验收记录写进 `docs/开发计划/Codex协作记录/`。
- 需求和阶段设计写进 `docs/需求文档/`。
- 阶段总状态和开发计划写进 `docs/开发计划/`。
- 可复用验收标准写进 `docs/验收清单/`。
- 已确认的排查经验写进 `docs/调试问题/`。
- 架构、代码规范、测试和发布约定写进 `docs/development/`。
- 不要把一次性提示词塞进长期规则。
- 复杂任务使用多角色流程，小任务保留基本顺序即可。

## 11. 新 rules 放哪里

新增规则时按用途放置：

- 每次都要遵守的长期规则，放进 `AGENTS.md`。
- 某个角色专属规则，放进对应的 `.codex/agents/*.toml`。
- 某类任务的固定流程规则，放进 `.codex/skills/*/SKILL.md`。
- 某一轮任务的计划、执行和验收记录，放进 `docs/开发计划/Codex协作记录/`。
- 业务需求和阶段设计，放进 `docs/需求文档/`。
- 阶段总计划、P 阶段状态和里程碑，放进 `docs/开发计划/`。
- 真机验收、回归检查和可复用测试步骤，放进 `docs/验收清单/`。
- 已确认的调试问题、复现步骤、根因和修复经验，放进 `docs/调试问题/`。
- 架构、代码、测试和发布等工程规范，放进 `docs/development/`。

不建议再新建根目录 `rules/`，避免和 `AGENTS.md`、`.codex/agents/`、
`.codex/skills/` 形成重复规则源。
