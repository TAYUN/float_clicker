# 新对话交接提示词

## 1. 用途

当需要在新的 Codex / GPT 对话中继续 Float Clicker 项目时，可以把本文档中的提示词作为开场消息发送给新 AI。

目标：

- 让新 AI 先阅读项目文档和当前代码。
- 避免新 AI 不理解现有单点模式进度就直接大规模改动。
- 明确下一阶段开发边界。
- 明确多点模式已经完成需求讨论和阶段拆分，后续按阶段推进。
- 保留“先分析、确认后再编码”的协作节奏。

## 2. 推荐开场提示词

```text
你现在接手 D:\code-my\float_clicker\float_clicker 项目。

请先阅读这些文档，理解当前进度，不要马上写代码：
- docs/需求文档/单点模式需求文档.md
- docs/需求文档/悬浮交互模式设计文档.md
- docs/需求文档/全局悬浮外观配置设计文档.md
- docs/需求文档/多点模式前置设计文档.md
- docs/需求文档/悬浮多点多配置执行设计文档.md
- docs/开发计划/多点模式开发阶段管理.md
- docs/验收清单/单点模式真机验收清单.md
- docs/调试问题/悬浮窗横竖屏贴边问题.md

当前项目状态：
- 单点模式已经基本稳定，已完成三态任务调度 idle/running/paused。
- 已完成普通/简洁/极简三种悬浮交互模式。
- 已完成 Overlay 组件拆分。
- 已完成全局悬浮外观配置，支持悬浮点位、控制条、独立控件分别缩放。
- 已处理 dispatchGesture 返回 false 的收尾。
- 已给 OverlayWindowHelper 加安全窗口操作封装。
- 已处理多轮悬浮窗横竖屏/跨应用边界问题，相关经验记录在 docs/调试问题/悬浮窗横竖屏贴边问题.md。
- 主页系统返回键已调整为 App 退到后台，不主动关闭悬浮窗。
- 单点模式真机验收基本通过。
- 多点模式需求分析和开发阶段拆分已经完成。
- 基础多点第一版边界已确认：只做多个固定点位按顺序点击。
- 后期“多配置管理 + 多执行入口”已单独建档，不进入基础多点第一版。
- P1：Flutter 多点模型与持久化已完成。
- P2：Flutter 多点页面已完成。
- P3：Android 多点 Overlay 已完成，包含多点点位显示、控制组件复用、位置回传、横竖屏、互斥、权限撤销和窗口异常边界。
- P4：通用手势执行与调度已进入进行中，已拆分为 P4.1-P4.4。
- 当前推荐下一步是 P4.1：通用动作和手势执行器。

开发原则：
- 先分阶段，不要大规模重写。
- 写代码前先检查 git status，避免覆盖我已有改动。
- 代码里加合适的中文注释。
- 优先复用单点模式已经稳定的模型、悬浮交互、全局外观和异常收尾逻辑。
- 基础多点第一版只做多个固定点位按顺序点击。
- 长按、滑动、延迟、复杂连招先只在架构上预留，不进入第一版 UI。
- 多配置执行、多执行控件、配置导入导出、防误触增强都属于后期阶段。
- 每个阶段完成后需要更新 docs/开发计划/多点模式开发阶段管理.md 的状态标记。
- 设计可以随开发迭代调整，但调整前要说明原因、影响范围，并同步更新需求、计划和验收标准。

请先输出：
1. 你理解的当前项目进度
2. 下一阶段推荐从哪里开始，是否仍是 P4.1
3. P4.1 第一阶段应该改哪些文件
4. 风险点

等我确认后再编码，（切记）。
```

## 3. 准备直接开发 P4.1 时的提示词

如果已经确认要开始 P4.1：通用动作和手势执行器，可以使用下面这段：

```text
你现在接手 D:\code-my\float_clicker\float_clicker 项目。

请先快速阅读这些文档，确认项目现状：
- docs/需求文档/单点模式需求文档.md
- docs/需求文档/悬浮交互模式设计文档.md
- docs/需求文档/全局悬浮外观配置设计文档.md
- docs/需求文档/多点模式前置设计文档.md
- docs/需求文档/悬浮多点多配置执行设计文档.md
- docs/开发计划/多点模式开发阶段管理.md
- docs/验收清单/单点模式真机验收清单.md
- docs/调试问题/悬浮窗横竖屏贴边问题.md

然后阅读这些关键代码：
- android/app/src/main/kotlin/com/example/float_clicker/SinglePointClickScheduler.kt
- android/app/src/main/kotlin/com/example/float_clicker/FloatClickerAccessibilityService.kt
- android/app/src/main/kotlin/com/example/float_clicker/SinglePointOverlayManager.kt
- android/app/src/main/kotlin/com/example/float_clicker/MultiPointOverlayManager.kt

当前阶段是 P4.1：通用动作和手势执行器。

范围只包括：
- 定义 `AutomationAction`，第一版只包含 tap 动作。
- 新增或抽出 `AccessibilityGestureExecutor`。
- 统一处理 `dispatchGesture()` 返回 false、完成、取消和无障碍服务断开。
- 保持单点模式现有行为不回退。
- 为 P4.2 多点调度器预留接口，但不要在 P4.1 直接接入多点 UI。

不要做：
- 不接入 `start/pause/resume/endMultiPointClicking` 的真实多点调度。
- 不实现 `MultiPointClickScheduler` 或轮次进度，这属于 P4.2。
- 不改多点页面交互和暂停编辑语义，这属于 P4.3/P4.4。
- 不实现长按、滑动、延迟动作 UI。
- 不实现多配置 profile、多执行控件、导入导出。
- 不大规模重写单点调度器；如果需要抽取，必须保持单点行为和测试通过。

开发要求：
- 先检查 git status。
- 不覆盖已有未提交改动。
- 优先复用单点模式已稳定的 dispatchGesture 收尾逻辑。
- 写代码时加合适中文注释。
- 完成后运行 flutter analyze、flutter test、flutter build apk --debug。
- 完成后更新 docs/开发计划/多点模式开发阶段管理.md 中 P4.1 的任务状态。
```

## 5. 当前多点模式关键决策

新 AI 接手时需要特别注意这些已确认决策：

- 基础多点第一版只做多个固定点位按顺序点击。
- 第一版默认创建 2 个启用点位，最多支持 12 个点位。
- 点位坐标持久化保存悬浮组件左上角，Android 执行点击时换算中心点。
- 不允许删除到 0 个点位对象；允许禁用全部点位，但执行和继续会被拒绝。
- 悬浮层第一版只显示启用点位，禁用点位只在 App 列表中展示。
- `running` 状态只允许拖动点位、切换悬浮交互和调整全局外观，不允许新增、删除、启禁、排序或修改点击参数。
- `paused` 状态允许完整编辑；如果点位结构变化，继续时保留已完成轮次，并从当前轮第一个启用点位重新开始。
- 单点和多点同一时间只允许一个模式开启；多点遇到单点已开启时返回 `mode_conflict`，不自动切换。
- 多点 Overlay 已完成，P4 之前的 `start/pause/resume/endMultiPointClicking` 仍不能假装可执行。
- 多点 Overlay 创建任一窗口失败时必须回滚，并返回 `overlay_window_unavailable`。
- 悬浮窗权限撤销时，单点和多点都必须安全退出并通知 Flutter 刷新权限/模式状态。
- P4 已拆分为 P4.1-P4.4；P4.1 只做通用 tap 动作和手势执行器，不直接接多点 UI。
- 首页运行状态后续需要升级为全局 active mode 状态，覆盖单点和多点。
- 后期多配置执行使用 `MultiPointProfile`，但不进入基础多点第一版。
- 多配置执行允许加载多个配置到悬浮执行区，但同一时间仍只执行一个任务。

## 6. 文档地图

建议新 AI 按下面顺序阅读：

1. `docs/需求文档/单点模式需求文档.md`：理解单点模式完整需求和已稳定能力。
2. `docs/需求文档/悬浮交互模式设计文档.md`：理解普通、简洁、极简三种交互形态。
3. `docs/需求文档/全局悬浮外观配置设计文档.md`：理解全局外观配置和跨模式复用。
4. `docs/需求文档/多点模式前置设计文档.md`：理解基础多点第一版核心设计。
5. `docs/需求文档/悬浮多点多配置执行设计文档.md`：理解后期多配置执行，不要混入第一版。
6. `docs/开发计划/多点模式开发阶段管理.md`：确认当前阶段、已完成任务和下一步。
7. `docs/验收清单/单点模式真机验收清单.md`：多点开发中要保护单点回归。
8. `docs/调试问题/悬浮窗横竖屏贴边问题.md`：理解 Overlay 边界和横竖屏策略。

## 7. 是否需要做成 Skill

当前建议：先放在 `docs/AI协作` 中，不急着做成 skill。

原因：

- 这类提示词强依赖当前项目进度，项目文档比 skill 更容易随需求同步更新。
- 新 AI 接手时需要的是项目上下文，而不是跨项目通用能力。
- 文档可以直接和需求、验收清单放在一起，版本管理更清晰。

适合做成 skill 的情况：

- 这套交接方式已经稳定，并且会在多个项目复用。
- 需要固定流程，例如“阅读文档 -> 检查 git -> 输出阶段计划 -> 等确认 -> 编码 -> 运行测试”。
- 希望新对话中只说一句“使用项目交接 skill”，AI 就能按固定流程工作。

如果后续要做成 skill，建议内容不要绑定 Float Clicker 的具体需求，而是抽象为：

```text
项目接手流程
- 读取项目文档
- 检查 git 状态
- 总结当前进度
- 识别下一阶段边界
- 输出改动文件和风险点
- 等用户确认后再编码
```

Float Clicker 的具体路径、当前进度和阶段目标仍然保留在项目文档中。

## 8. 维护建议

- 每完成一个大阶段后，更新本文档中的“当前项目状态”和“准备直接开发时的提示词”。
- 每新增重要需求文档或验收清单后，把路径加入推荐开场提示词。
- 如果某阶段已经完成，不要让提示词继续要求新 AI 从旧阶段开始。
- 如果要让新 AI 直接编码，必须明确“本阶段包含什么”和“本阶段不包含什么”。
- 阶段状态以 `docs/开发计划/多点模式开发阶段管理.md` 为准。
