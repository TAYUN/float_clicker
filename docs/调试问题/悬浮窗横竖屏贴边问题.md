# 悬浮窗横竖屏贴边问题

## 背景

单点模式的点击点、控制条、收起图标和独立执行控件都是 Android `WindowManager` 悬浮窗。用户会在 Float Clicker 竖屏页面开启单点模式，然后切换到其他竖屏或横屏 App 中拖动悬浮组件。

## 问题现象

- 从竖屏切换到横屏应用后，悬浮点或控制条有时无法继续向右拖动，常见表现是距离右边还有约 2/5 屏宽时就被卡住。
- 早期修复中，横竖屏后首次拖动需要拖很远，控件才会从屏幕边缘脱离。
- 尝试用 `getLocationOnScreen()` 同步 `WindowManager.LayoutParams.x/y` 后，控件虽然能立即移动，但一拖动就会瞬间跳到手指右下方。
- 使用动态 `rootWindowInsets` 避让系统栏时，不同悬浮组件拿到的 inset 不一致，导致控制条有时避让状态栏，而悬浮点不避让。

## 原因分析

- `WindowManager.LayoutParams.x/y` 和 `View.getLocationOnScreen()` 不属于完全相同的坐标语义，不能直接互相写回。
- 切到其他横屏 App 时，`context.resources.displayMetrics` 有时仍反映 Float Clicker 自身的竖屏配置，用它计算边界会把横屏拖动范围误限制成竖屏宽度。
- 悬浮窗在其他 App 上方运行时，Activity 的 `onConfigurationChanged()` 不一定覆盖所有显示变化，所以仅依赖 Activity 配置变化刷新不够。
- 系统状态栏、导航栏和刘海区的可见性在不同 App 中差异较大，如果每个 overlay view 动态读取 inset，容易出现组件之间规则不一致。

## 最终策略

- 悬浮窗使用整屏布局参数：
  - `FLAG_LAYOUT_IN_SCREEN`
  - `FLAG_LAYOUT_NO_LIMITS`
  - Android P+ 设置 `LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES`
- 边界尺寸优先读取默认 Display 的实时尺寸：
  - `DisplayManager.getDisplay(Display.DEFAULT_DISPLAY)`
  - `display.getRealSize(Point)`
  - 只有读取失败时才回退到 `context.resources.displayMetrics`
- 竖屏采用确定性边界：
  - 左边界为 `0`
  - 顶部统一避让系统 `status_bar_height`
  - 右/下按实时屏幕尺寸限制
- 横屏采用放宽边界：
  - 左/上不允许小于 `0`
  - 右/下边界放宽，避免系统返回竖屏宽度时把控件卡在横屏中间
  - 如横屏拖得过远，用户可切回竖屏调整位置
- 拖动开始、拖动过程中、配置回放时都走同一套边界计算，避免不同入口产生不同位置规则。
- OverlayManager 注册 `DisplayManager.DisplayListener`，默认屏幕变化时主动刷新悬浮组件位置。

## 踩坑记录

- 不要把 `getLocationOnScreen()` 的结果直接写回 `WindowManager.LayoutParams.x/y`，会产生坐标系偏移，拖动时控件会跳位。
- 不要只用 `context.resources.displayMetrics` 判断横竖屏和边界，它在切到其他 App 后可能不是当前默认 Display 的真实方向。
- 不要让不同悬浮组件各自动态决定是否避让状态栏，容易出现点击点和控制条规则不一致。
