# P5 多点联调与真机验收

## Summary
按你定的主线推进 P5：以主对话统一判断当前真实状态，Explorer/Tester/Builder/Reporter 作为辅助角色按需介入，不默认派生工作树。  
P5 以“代码先行、只修明确问题”为原则，先把现有 P4 完整跑通，再进入真机验收、回归和风险收敛，重点保护单点模式不回退。

## Implementation Changes
- 先做代码层回归和状态核对：确认 `MultiPointClickScheduler`、`MultiPointOverlayManager`、`MainActivity`、`MultiPointPage`、`AndroidPermissionService` 这条链路在当前基线上行为一致。
- 跑通并记录标准检查：`flutter analyze`、`flutter test`、`flutter build apk --debug`，先把可编译、可测试、可构建作为 P5 的第一道门槛。
- 按真机验收清单逐项验证多点模式的核心链路：
  - 权限缺失与恢复
  - 开启/暂停/继续/结束
  - 点位拖动与持久化
  - 横竖屏切换
  - 悬浮窗权限撤销
  - 无障碍服务断开
  - 单点模式回归
- 如果验收中发现明确问题，只做最小修复，不扩展到新功能、不进入 P6/P7/P8。
- 验证后更新 `docs/开发计划/多点模式开发阶段管理.md`：
  - P5 状态推进
  - 记录已验收项、未完成项和风险
  - 保持 P4 结果可追溯

## Test Plan
- 自动化回归：
  - `flutter analyze`
  - `flutter test`
  - `flutter build apk --debug`
- 手动真机验收：
  - 多点模式开启、执行、暂停、继续、结束
  - 暂停后编辑点位/设置，再继续
  - 权限撤销与恢复
  - 无障碍断开后的收尾
  - 横竖屏切换
  - 单点模式完整回归
- 只要出现失败，就优先判断是：
  - 原生状态不同步
  - Flutter 快照读取时机不对
  - 权限/服务边界处理不完整
  - 测试 mock 与真实行为有偏差

## Assumptions
- 默认采用“代码先行”主线：先做静态检查和构建，再做真机验收。
- 默认采用“只修明确问题”：P5 只修验收中确认的 bug，不主动做文档外优化。
- 不派生工作树，除非后续出现需要并行试验的高风险修复。
- 不扩大到 P6/P7/P8。
- 单点模式回归优先级与多点验收同级，不能因为 P5 把单点稳定性拖下去。
