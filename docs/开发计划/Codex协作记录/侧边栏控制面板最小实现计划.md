# 侧边栏控制面板最小实现计划

## Summary

- 基于《侧边栏控制面板交互方案草案》《侧边栏控制面板低保真原型说明》和《侧边栏控制面板文字线框图》，本轮开始把交互方案收敛为一个可实施的小阶段计划。
- 本计划只定义“侧边栏只做全局控制壳”的第一轮最小实现范围，不直接进入更重的交互重构。
- 本计划仍以保护 P7 已验证链路为前提：不改变多配置 profile 真实执行语义，不进入 `P8` 动作能力，不引入并行执行或新的复杂设置项。

## Stage Positioning

- 当前不建议直接把侧边栏实现并入 `P8`。
- 建议将本轮视为 **P7 收口后的独立交互演进小阶段**，先验证“全局控制壳”是否值得保留，再决定是否扩大实现范围。
- 本计划通过后，再单独进入实现；实现完成后再补自动化验证和真机验收记录。

## Recommended Scope

本轮最小实现建议只包含以下能力：

1. 新增一个侧边栏控制面板壳层，用于承载多配置执行区的全局状态和全局操作。
2. 第一轮只实现三个核心可交付状态：
   - 收起态入口
   - 展开态空闲中
   - 展开态运行中
3. 展开态运行中提供一个明确的“停止当前任务”入口。
4. 展开态空闲中只提供状态摘要和说明，不承载 profile 列表或 profile 点击执行。
5. 保留现有外部圆形执行控件，继续作为 profile 的真实启动入口。

## Out Of Scope

本轮明确不做：

- 不实现侧边栏内的 profile 列表或 profile 切换。
- 不把外部圆形执行控件收敛进侧边栏内部。
- 不实现“更多操作”真实功能；第一轮最多保留占位文案，或在实现时直接去掉。
- 不新增 Flutter 页面配置项。
- 不引入新的 MethodChannel 能力，除非实现过程中确认 Android 侧无法复用现有状态。
- 不实现异常提示态专门 UI；第一轮继续沿用已验证的 Toast 和安全收尾语义。
- 不改动单点模式链路。
- 不进入 `P8` 长按、滑动、延迟和高级连招。

## Default Assumptions

为避免计划阶段边界漂移，本轮先采用以下默认假设：

1. 侧边栏入口优先复用当前已存在的全局执行区入口语义，而不是额外再新增一个独立悬浮入口。
2. 侧边栏第一轮主要由 Android Overlay 侧承载，尽量不改 Flutter 数据模型和持久化结构。
3. 当前运行中的 profile 名称、已加载 profile 数量和任务状态，应优先从现有多配置执行状态中派生，不新增新的 profile 同步协议。
4. 若实现时发现必须引入新的跨端协议，需先回到计划文档补充影响范围，再决定是否继续。

## UI Scope Breakdown

### A. 收起态入口

第一轮只需要做到：

- 入口具备“全局控制壳”语义，而不是某个 profile 的单独按钮语义。
- 点击入口可展开侧边栏。
- 运行中可显示极简状态提示，但不堆叠复杂信息。
- 拖动、位置持久化和横竖屏可见校正继续沿用现有能力。

### B. 展开态空闲中

第一轮只需要做到：

- 展示“多配置执行区”标题。
- 展示“空闲中”状态。
- 可选展示已加载 profile 数量。
- 明确提示真正执行入口仍是外部圆形执行控件。
- 提供收起入口。

### C. 展开态运行中

第一轮只需要做到：

- 展示“运行中”状态。
- 展示当前运行 profile 名称。
- 提供“停止当前任务”入口。
- 提供收起入口。

## Plan

1. 先确认入口复用策略：默认复用现有全局执行区入口，不新增第二个全局悬浮入口。
2. 梳理 `MultiProfileExecutionOverlayManager` 当前对 launcher、按钮组显示/隐藏、运行状态和当前 profile 的管理方式，确认哪些状态可直接复用。
3. 设计侧边栏面板组件最小结构，优先拆成独立组件，避免把面板布局直接塞进 manager。
4. 接入展开态空闲中与运行中两种面板状态，先不做异常专门面板。
5. 接入“停止当前任务”入口，复用现有停止链路，不新增停止协议。
6. 补最小自动化验证方案，确认 analyze、test、build 和 `git diff --check` 要求。
7. 产出真机验收项，重点验证收起/展开、运行中状态、停止入口、异常收尾和单点回归。

## Acceptance Criteria

- 开启多配置执行区预览后，存在一个可识别的全局控制壳入口。
- 点击入口后可展开侧边栏控制面板。
- 空闲态面板至少能展示空闲状态，并明确说明执行入口仍是外部圆形执行控件。
- 运行中面板至少能展示当前运行状态、当前 profile 名称和“停止当前任务”入口。
- 点击“停止当前任务”后，任务安全结束，并回到空闲态表现。
- 外部圆形执行控件仍保留，并继续作为 profile 真实启动入口。
- 现有拖动、位置持久化、横竖屏可见校正、异常收尾和单任务互斥行为不回退。
- 单点模式最小回归不受影响。

## Verification Plan

如果进入实现，计划至少执行：

- `flutter analyze`
- `flutter test`
- `flutter build apk --debug`
- `git diff --check`

真机验收建议至少覆盖：

- 收起态入口展开与收起。
- 空闲态查看。
- 点击外部执行控件后，运行中侧边栏状态是否正确。
- 从侧边栏点击“停止当前任务”后任务是否安全结束。
- 运行中无障碍断开或悬浮窗权限撤销后，异常收尾是否仍正常。
- 横竖屏切换后入口和侧边栏是否保持可见或可恢复。
- 单点模式最小回归。

## Risks

- 如果当前 launcher 语义与侧边栏入口语义差异过大，复用入口可能导致交互心智不够直观。
- 如果 manager 当前没有稳定持有“已加载数量 / 当前运行 profile 名称 / 展开态状态”这些 UI 所需信息，第一轮可能被迫引入新的状态桥接。
- 如果侧边栏展开后遮挡明显，可能需要比预期更早处理布局尺寸和贴边策略。
- 若实现过程中发现“外部执行控件 + 侧边栏”依然过于分散，可能需要回到方案层重新评估是否进入方案 B。

## Open Questions

在进入实现前，建议优先确认以下问题：

1. 收起态入口主标签更适合用 `执行区`、`控制`，还是只保留图标与极短状态。
2. 空闲态是否保留“已加载 X 个配置”这条信息，还是进一步收敛为只显示空闲状态。
3. 第一轮是否保留“更多操作”占位；若无明确价值，建议实现阶段直接去掉。
4. 展开侧边栏后，外部圆形执行控件是否始终保持可见，还是在某些状态下做轻量弱化。

## Recommended Decisions

为便于进入实现，当前建议先采用以下默认答案：

1. 收起态入口主标签默认使用 `执行区`。
   - 原因：相比 `控制`，`执行区` 更贴近当前多配置执行场景，也更容易与单个 profile 按钮区分。
   - 第一轮不建议只保留图标，否则“这是全局入口还是某个执行按钮”仍然可能不够直观。
2. 空闲态默认保留“已加载 X 个配置”。
   - 原因：这条信息成本低，但能帮助用户快速建立“这是多配置执行区全局壳层”的认知。
   - 如果真机观察发现信息密度仍偏高，再回退为只显示空闲状态。
3. 第一轮实现不保留“更多操作”占位。
   - 原因：当前没有明确要挂接的真实功能，占位只会增加认知负担，也容易让用户误以为功能未完成或入口失效。
   - 该扩展位继续只保留在文档层，不进入首轮 UI。
4. 展开侧边栏后，外部圆形执行控件默认继续保持可见，不做主动弱化。
   - 原因：第一轮目标是验证“全局控制壳”是否有价值，而不是同时改造现有真实执行入口的视觉层级。
   - 如果后续真机反馈确认“侧边栏 + 外部控件”同时显示过于拥挤，再单独评估轻量弱化或进入方案 B。
